# 02 公共协议层（internal/common）

## 1. 包定位

`internal/common` 是两端共用的**协议层**：全部线缆格式的类型定义、校验与编解码都集中在此。包的硬性约束（见 `internal/common/doc.go`）：

- **无状态**：不持有任何会话/链路状态；
- **无并发**：不起 goroutine，全部函数可并发调用；
- **无 I/O**：不碰网络与文件，只做纯转换；
- **常量两端共用**：消息上限、端口数、MTU 上限等协议常量定义在本包，客户端与服务端引用同一份，杜绝两端各写一个数字后漂移。

`Validate` 的边界：做**结构校验**（字段形状、长度、枚举值），不做业务判断（设备是否存在、配对是否成立）。允许未知字段，拒绝畸形结构。

## 3. 三条独立线缆协议

| 协议 | 载体 | 方向 | 格式 |
|---|---|---|---|
| 控制协议 | 单条 TCP 连接 | 客户端 ↔ 服务器 | JSON Lines（每行一条 JSON 消息） |
| 探测协议 | UDP × 5 端口 | 客户端 → 服务器 | ASCII 文本 `PROBE` / `PORT` |
| 数据协议 | UDP P2P（打洞 socket） | 客户端 ↔ 客户端 | 二进制 GTUN 帧 + ASCII P2P 控制包，**同 socket 多路复用** |

数据面 socket 的多路复用规则：报文前 4 字节等于 ASCII `"GTUN"` 即数据帧，否则按 P2P 控制包解析。两类报文天然可区分——P2P 控制包 ≤64 字节、全部可打印 ASCII 且不以 "GTUN" 开头（类型字 PUNCH/PING 等）。

## 4. GTUN 数据帧（UDP 数据面）

定义在 `internal/common/gtun.go`。固定 **16 字节头 + 变长 payload**，多字节整数一律**大端序**：

```
 0               4               10              14    16
 +---------------+---------------+---------------+-----+---------------------+
 | magic "GTUN"  | token (6B)    | sequence (4B) | len | 内层 IPv4 包 (N 字节)|
 +---------------+---------------+---------------+-----+---------------------+
```

| 偏移 | 大小 | 字段 | 含义与取值 |
|---|---|---|---|
| 0 | 4 | magic | ASCII `"GTUN"`（0x47 0x54 0x55 0x4E），常量 `gtunMagic` |
| 4 | 6 | token | LinkToken 的 6 字节原始值（由 12 字符小写 hex 解码），标识一次链路尝试；接收端与本次尝试的 token 比对 |
| 10 | 4 | sequence | uint32 大端，发送方单调递增帧序号 |
| 14 | 2 | length | uint16 大端，payload 字节数；解码时必须等于 `len(datagram) − 16` |
| 16 | N | payload | 完整的内层 IPv4 包（含 IP 头） |

关键常量与设计决策：

- `GTUNHeaderBytes = 16`；`MaxTUNMTU = 65491 = 65535 − (IPv4 头 20 + UDP 头 8 + GTUN 头 16)`，保证整帧不超过 UDP 最大载荷。
- **sequence 仅供抓包对账**：接收端刻意不校验、不去重（`GTUNFrame.Sequence` 注释）。隧道承载的内层流量自带可靠性（TCP 重传兜住丢包），在 UDP 上再做一层序号判定是重复付费。
- **校验不对称**：`EncodeGTUNFrame` 不校验 payload 的 IPv4 结构与头校验和——出站包由本机内核经 TUN 交出，结构必然合法，且数据面入队前已验过一次，热路径再算一遍校验和纯属浪费；`DecodeGTUNFrame` 必须校验——数据来自网络，会有传输误码。
- 解码返回的 payload 是 datagram 的**副本**，防调用方复用接收缓冲后篡改已解码帧。
- token 的 6 字节宽度由帧头固定字段决定，`LinkToken` 的 12 hex 字符长度因此**不能改**（见第 9 节 ID 体系）。

### 内层 IPv4 校验规则（`ValidateIPv4Packet`）

解码路径对 payload 逐项检查：

1. 长度 ≥ 20 字节；
2. 版本号 = 4（首字节高 4 位）；
3. IHL = (首字节低 4 位) × 4，且 20 ≤ IHL ≤ 60 ≤ 包长；
4. IPv4 头部的 total length 字段与实际包长一致，且 ≥ IHL；
5. IPv4 头**一补和校验**通过（`validIPv4Checksum`：16 位字累加、折叠进位、结果应为 0xFFFF）。

## 5. TCP 控制面：JSON Lines

- 载体：单条 TCP 连接（服务端默认 `0.0.0.0:10000`），每条消息一行 JSON，`\n`（LF）结尾，行内容不含 LF。
- 上限：`MaxControlMessageBytes = 64 * 1024`（`tcp_message.go`），只计 LF 前字节；服务端 `control.go` 与客户端 `control.go` 都用它构造 `LineReader`。
- 分帧规则（`framing.go` 的 `LineReader.ReadLine`）：
  - 空行跳过；
  - 超长行返回 `ErrLineTooLong` 并**持续消费到下一个 LF**（防半行残留毒化后续解析）；
  - EOF 时有内容但无 LF，返回 `ErrUnterminatedLine`；
  - bufio 缓冲 = min(maxBytes+1, 64KB)。
- 编码：标准 `json.Unmarshal`，**允许未知字段**（向前兼容是刻意的双端决策——原版 DisallowUnknownFields 的严格校验被判定为过度防御，双端同仓同发，结构校验已足够）。
- 分发：按头部 `type` 字段路由（`DecodeMessage`），未知类型返回 `ErrUnknownMessageType`。
- nil slice 在编码侧统一为 `[]` 而非 `null`（`NetworkDefinition.MarshalJSON`、`StateReport.MarshalJSON`、`NATProfile.MarshalJSON`）——这是原版「nil/空语义区分导致缺陷」的修复方式：与其让解码端区分两种空，不如让编码端只有一种空。

### 5.1 消息类型全表（`tcp_message.go`）

上行（客户端 → 服务器）：

| type | 结构体 | 用途 |
|---|---|---|
| `device_register` | `DeviceRegister` | 一条连接的第一条消息：注册/刷新设备身份 |
| `device_heartbeat` | `DeviceHeartbeat` | 周期心跳，无业务字段（状态不搭心跳的车） |
| `device_unregister` | `DeviceUnregister` | 礼貌告别，收到即标离线但不拆隧道 |
| `state_report` | `StateReport` | 链路状态上报（全量快照 / QUERY 响应 / 即时转场三合一） |
| `profile_report` | `ProfileReport` | NAT 画像上报（带 token，属于特定尝试） |

下行（服务器 → 客户端）：

| type | 结构体 | 用途 |
|---|---|---|
| `device_registered` | `DeviceRegistered` | 注册确认，仅 type |
| `duplicate_login` | `DuplicateLogin` | 发给被顶替的旧连接；客户端视为进程级终态 |
| `network_config` | `NetworkConfig` | 全量网络配置推送（注册后紧随推送；配置变更后重推） |
| `connect` | `Connect` | 建链意图：token + peering_id + 对端{device_id,name,ip}，同一 token 发给双方 |
| `disconnect` | `Disconnect` | 拆链意图：客户端按 peering_id 执行，token 仅日志比对 |
| `peer_profile` | `PeerProfile` | 对端 NAT 画像（服务器配对后互发） |
| `query` | `Query` | 要求该客户端回全量 StateReport |
| `error` | `ErrorMessage` | 服务器终止会话前的最后一条消息 |

### 5.2 关键结构详解

**DeviceRegister**：`device_id`（36 字符规范 UUID 文本）+ `name`（1..128 UTF-8 字符）+ `platform`（枚举 `linux|darwin|windows`）。

**NetworkConfig / NetworkDefinition / NetworkPeer**：

```json
{"type":"network_config","network":{
  "id":"130fe21c","name":"lan","cidr":"10.206.0.0/24","ip":"10.206.0.1",
  "peers":[{"device_id":"...","peering_id":"...","name":"debian-b","ip":"10.206.0.2","online":true}]}}
```

`network` 可为 `null`（设备不属于任何网络）。校验：CIDR 内本地 IP 可用；peer 的 device_id / peering_id / ip 三个集合各自无重复。**刻意没有版本/代次字段**——不变量是「配置推送始终全量」（删除 revision 的完整论证见 [07-存储与管理面.md](07-存储与管理面.md)）。

**StateReport / LinkReport**：`full bool` + `links[]`，每条 `{peering_id, state, token, reason?}`。状态三值 `IDLE|CONNECTING|CONNECTED`。按 Full 校验字段组合：

| full | 语义 | 约束 |
|---|---|---|
| true | 全量快照 | 每条 peering 一条；IDLE ⇔ 空 token |
| false | 即时转场 | 必须带 token；state 只许 CONNECTED（成功）或 IDLE（失败，可带 reason） |

**NATProfile / ProfileReport / PeerProfile**：画像 `{nat: "stable"|"variable", public_ip, ports[5]}`，结构不变量：**五端口全等 ⇔ stable**。ProfileReport 与 PeerProfile 都带 token + peering_id——画像属于特定尝试。

**ErrorMessage**：`code` 封闭五值 `invalid_message | unknown_type | register_timeout | server_full | internal_error`，`message` 1..512 字节。注意与链路失败原因（第 10 节 Reason，大写域）和 HTTP 管理错误码（小写蛇形域，见 [07-存储与管理面.md](07-存储与管理面.md)）三个域互不混用。

**Endpoint**：`ip` + `port`，当前仅作为预留扩展（后续若需要服务器显式通告端点）。

## 6. P2P 控制包（打洞握手）

定义在 `internal/common/p2p_control.go`。ASCII 文本、空格分隔，与 GTUN 帧同 socket 传输：

- 上限 `MaxP2PControlDatagram = 64` 字节；
- 全部字节必须可打印 ASCII（0x20–0x7E），无 LF；
- 字段间**恰好单个空格**（连续空格、首尾空格均拒绝）。

| 类型 | 布局（空格分隔） | 校验要点 |
|---|---|---|
| `PUNCH` | `PUNCH <token> <sender_socket_id>`（3 字段） | target 必空、seq=0 |
| `PUNCH_ACK` | `PUNCH_ACK <token> <target_socket_id> <sender_socket_id>`（4 字段） | 三 ID 均有效、seq=0 |
| `PUNCH_OK` | `PUNCH_OK <token> <target_socket_id> <sender_socket_id>`（4 字段） | 同 ACK |
| `PING` | `PING <token> <sequence>`（3 字段） | sequence 为无符号十进制 uint32；target/sender 必空 |

`sender_socket_id` 声明「本包从哪个 socket 发出」——接收端校验它必须等于实际到达的 socket，防止 helper 批量发包时错位（zip 错位回归有单测钉住）。握手的状态机与使用方式见 [05-NAT穿透与打洞.md](05-NAT穿透与打洞.md)。

## 7. 探测包（PROBE / PORT）

定义在 `internal/common/probe.go`。上限 `MaxProbeDatagram = 256` 字节；`ProbePortCount = 5`（一次画像 = 同一 socket 向服务器 5 个连续 UDP 端口各发一个 PROBE）。

| 方向 | 格式 | 字段约束 |
|---|---|---|
| 请求 | `PROBE <nonce> <probe_id>`（3 字段） | nonce = 恰好 16 个小写 hex（客户端随机生成，响应须原样回显——双重校验挡回显伪装）；probe_id = 规范十进制（无前导零）1..5，与 5 个探测端口一一对应 |
| 响应 | `PORT <nonce> <probe_id> <public_ip> <mapped_port>`（5 字段） | public_ip 规范 IPv4 文本；mapped_port 1..65535 |

格式错误的报文由端点**静默丢弃**（畸形输入不值得回应，探测反射器侧另有按源 IP 的日志限流）。

## 8. 刻意不存在的机制

`doc.go` 明示三条，防止回头加回去：

1. **无尝试编号（attempt number）**：LinkToken 已唯一标识一次链路尝试，attempt 序号是冗余标识。
2. **无会话/请求关联 ID**：一条 TCP 连接只注册一次，靠 TCP 有序可靠，请求与响应不需要关联字段。
3. **无配置代次（revision）**：配置推送始终全量，幂等由「拓扑未变不重建 + 重建前先拆干净」保证（完整论证见 [07-存储与管理面.md](07-存储与管理面.md) 第 2.2 节，重建语义见 [04-客户端.md](04-客户端.md) 第 4.2 节）。

（另：ID 生成无碰撞检测的取舍记录在 [01-系统架构总览.md](01-系统架构总览.md) 第 8 节对照表，不单列。）

## 9. ID 体系（`id.go`）

| 类型 | 长度 | 生成 | 用途 | 生命周期 |
|---|---|---|---|---|
| `DeviceID` | 36 字符规范 UUID（小写带连字符） | `uuid.NewString()` | 设备持久身份，devices 表主键 | 客户端身份文件自持，永生 |
| `NetworkID` | 8 hex（4 字节） | `randomHex(4)` | 虚拟网络身份 | 落库 |
| `PeeringID` | 32 hex（16 字节） | `randomHex(16)` | 一对设备的配对身份 | **配置数据，落库，跨多次建链** |
| `LinkToken` | 12 hex（6 字节） | `randomHex(6)` | 一次链路尝试 | 随 CONNECT 生成，随失败/拆链丢弃，不落库 |
| `SocketID` | 8 hex（4 字节） | `randomHex(4)` | 一个 Worker 内的 UDP socket | 尝试内 |

**PeeringID 与 LinkToken 的区分**是设计要点：数据面按 token 认帧（GTUN 帧头 6 字节），控制面按 peering 认配置。token 宽度被帧头钉死，改 token 长度必须同步改帧格式。

- `ParseDeviceID` 要求 parse 后回写逐字相等（拒绝非规范形式的大写/非标准连字符）。
- 截短 ID（NetworkID/LinkToken/SocketID）校验：固定长度小写 hex（`validateHexID`）。
- **`Link [2]DeviceID`**：两设备按**字典序规范化排序**（`NewLink` 拒绝相等/非法 ID；`UnmarshalJSON` 强制恰 2 元素且已规范化）。同一对设备在服务器内存表、SQLite 的 `network_peerings`（CHECK `device_a < device_b`）、两端日志里有唯一表示。

## 10. 链路失败原因码（`reason.go`）

封闭 12 值，`ValidateReason` 拒绝空值/超 200 字节/表外值：

| Reason | 含义 |
|---|---|
| `PROBE_TIMEOUT` | 探测超时（预算内未完成五端口画像） |
| `PROBE_IP_CHANGED` | 五端口回显公网 IP 不一致（家宽按流轮换出口）。现行客户端不以此失败（处置见 [05-NAT穿透与打洞.md](05-NAT穿透与打洞.md) 第 2 节），此值仅为协议封闭集保留 |
| `PUNCH_TIMEOUT` | 打洞预算内未完成握手 |
| `NAT_UNSUPPORTED` | 双方均 variable，打洞前预判拒绝 |
| `ROUTE_CONFLICT` | 路由预检冲突 |
| `TUN_CREATE_FAILED` | TUN 设备/栈创建失败 |
| `CONFIG_INVALID` | 配置无效（含 helper_count 非法档位，仅启动校验阶段） |
| `TUNNEL_LOST` | 已建成隧道保活失活（任一侧上报即判失败） |
| `PEER_OFFLINE` | 一侧控制连接离线，拒绝下发 CONNECT/DISCONNECT |
| `HANDSHAKE_FAILED` | 握手失败 |
| `QUEUE_FULL` | 队列满 |
| `INTERNAL_ERROR` | 内部错误 |

刻意**没有** `CONTROL_DISCONNECTED`：控制面断开不影响隧道，把它加进 Reason 等于承认服务器可凭连接状态改链路状态——那正是被删除的 RECOVERING 思路。

## 11. 标量类型（`scalar.go`）

| 类型 | 校验 |
|---|---|
| `IPv4` | `netip.ParseAddr` 成功、Is4、`String()` 与原文逐字相等（拒绝 `010.1.1.1` 等非规范文本）、单播 |
| `IPv4CIDR` | masked（网络地址形式）、文本规范、首末地址均 IsPrivate（RFC1918）；`LastIPv4Address` 计算广播地址，供地址分配共用 |
| `Port` | 非零 uint16；`UnmarshalJSON` 拒零/负/小数/字符串/溢出 |
