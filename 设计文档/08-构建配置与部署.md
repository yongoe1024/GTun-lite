# 08 构建配置与部署（cmd / Makefile / 配置）

## 1. 入口流程

两端共同模式：`main` 只调 `os.Exit(run())`——os.Exit 不执行 defer，因此全部生命周期（含 defer 清理链）都在 `run` 内，返回值即退出码。

### 1.1 cmd/server/main.go

1. `-config` flag（默认 `server.yaml`）→ `LoadServerConfig`（严格 YAML，KnownFields）；
2. slog TextHandler → stderr（级别可配）；
3. `OpenStore`（SQLite；空库自动建表），defer Close；
4. `NewHub`（owner goroutine），defer Close；
5. 控制面 `Listen()`（同步绑定，失败即退出）；
6. `signal.NotifyContext(SIGINT, SIGTERM)`；
7. 探测反射器：5 端口绑定失败即退出（fail-fast）；
8. 管理面 `net.Listen`（同步绑定）；
9. goroutine 并发 serve 控制面与管理面；select 等待信号/错误；退出时管理面 Shutdown → 等 serve 结束。

完整组件语义见 [06-服务端.md](06-服务端.md) §3。

### 1.2 cmd/client/main.go

1. `-config` flag（默认 `client.yaml`）→ `LoadClientConfig`；
2. logger；
3. **第一个运行动作**：`EnsureHelperFDHeadroom`（fd 预算自举，见 [04-客户端.md](04-客户端.md) §9）；
4. `LoadIdentity`（首启生成并原子写回）；
5. `NewManager`，defer manager.Close（停 Worker、拆数据栈与 TUN/路由）；
6. `control.Run(ctx)` 阻塞运行；错误（含 duplicate_login 终态）退出码 1。

## 2. 配置

### 2.1 配置入门（改配置前先读）

三条规则：

1. **所有键都可以省略**，省了就用默认值。唯一例外是客户端的 `server.addr`：必填、无默认值——它是部署参数，猜一个只会掩盖「配置文件没读到」的问题。
2. **写错直接拒启动，不会静默失效**。两端都是严格 YAML：键名拼错、多写不存在的键、时长写成裸数字（`20` 而非 `20s`）都在启动时报错。拿不准就先跑起来看报错，比配了没生效好排查得多。
3. **部分键两端联动**，改一端必须同步改另一端，清单与配错现象见 §2.4。

首次上手的动手顺序：服务端只改 `database.path`（放数据盘）→ 客户端只填 `server.addr` 跑通 → 打洞不通再开客户端 `logging.level: debug` 看画像与握手日志、上调 `punch.helper_count` 档位 → 其余键在明确知道为什么之前不动。默认值就是推荐值。

### 2.2 服务端配置全表（cmd/server/server.yaml）

监听三个端口段：TCP 控制面（默认 10000）、UDP 探测 5 连端口（默认 10000–10004）、管理 API（默认 127.0.0.1:9090）。探测端口被占用属于部署错误，启动即失败。

| 键 | 默认 | 约束 |
|---|---|---|
| control.bind | 0.0.0.0:10000 | — |
| control.register_timeout | 10s | >0，未注册连接的沉默上限 |
| control.heartbeat_timeout | 60s | >0，须明显大于客户端心跳（20s） |
| control.write_timeout | 5s | >0（也是发送队列卡死上限） |
| control.max_connections | 1000 | ≥1，超出注册拒 server_full |
| probe.bind / probe.base_port | 0.0.0.0 / 10000 | 端口 1..65531（连续占 5 个） |
| admin.bind | 127.0.0.1:9090 | 不要绑公网（无鉴权） |
| database.path | gtun.db | 空库自动建表；结构不符拒绝启动 |
| limits.max_devices_per_network | 8 | ≥2；性能目标按 8 设计，调大前先读 §6 已知边界 |
| limits.min/max_cidr_prefix | 24/28 | 16≤min≤max≤29 |
| logging.level | info | debug/info/warn/error |
| logging.file / logging.error_file | 空/空（stderr） | 可选双文件落盘（info 及以下 / warn 及以上，追加写）；**随包 yaml 默认开启**（`gtun-*.log/.err`，删去或留空即回落 stderr）；路径打不开拒启动；两路径不得相同 |

交叉校验：设备上限 ≤ 最小网段可用主机数 `2^(32−max_prefix)−2`（防「/29 配 8 台、第 7 台入网才地址耗尽」的启动不报错矛盾）。心跳与客户端间隔的配比**刻意不做前置校验**——两端默认值不应形成隐性耦合，错配靠日志暴露。

### 2.3 客户端配置全表（cmd/client/client.yaml）

权限：Linux 需 root，macOS 需 sudo（TUN 设备创建）。Windows exe 内嵌 `requireAdministrator` manifest（源文件 `cmd/client/gtun-client.manifest`，经 `rsrc` 生成 `rsrc_windows_amd64.syso` 随构建自动链接）：双击运行即弹 UAC 提权；工作目录为 exe 所在目录，默认相对路径的配置与身份文件直接命中。macOS 默认 fd 软上限常见为 256，连默认档位 256 都装不下——先 `ulimit -n 4096` 或依赖启动自举抬高。

| 键 | 默认 | 说明 |
|---|---|---|
| server.addr | **必填** | 服务器控制面地址（IP 或域名:port） |
| server.probe_base_port | 10000 | 与服务端 probe.base_port 一致 |
| identity.path | gtun-device-id | 身份文件，首启生成 |
| identity.name | 主机名 | 注册显示名 |
| tun.name / tun.mtu | gtun0 / 1280 | mtu 合法区间 20..1456（=1500−44 外层开销：IPv4 20 + UDP 8 + GTUN 头 16） |
| tunnel.outbound_queue / inbound_queue | 1024 / 1024 | 固定长度队列（包数） |
| control.heartbeat_interval | 20s | 须小于服务端 heartbeat_timeout |
| control.register_timeout / connect_timeout | 10s / 10s | — |
| control.reconnect_interval | 5s | 固定间隔，无指数退避 |
| control.write_timeout | 5s | — |
| probe.timeout / per_port_timeout / retries | 30s / 1s / 3 | 五端口画像总预算（串行 5 端口、每端口含重试最多 4 次等待，1s×4×5=20s 装进 30s） |
| punch.stable_timeout / variable_timeout | 5s / 15s | 直连 / variable 侧（helper 信标+Range 备援）预算 |
| punch.helper_count | 256 | 256/512/1024 三档，其他值拒绝启动 |
| logging.level | info | — |
| logging.file / logging.error_file | 空/空（stderr） | 可选双文件落盘（同服务端）；随包 yaml 默认开启，schtasks/服务化部署不依赖启动器重定向 |

### 2.4 跨端部署检查（启动前）

- **端口匹配**：客户端 `server.addr` 与 `server.probe_base_port` 与服务端 `control.bind` / `probe.base_port` 一致。配错的现象：addr 端口错 → 连不上、固定间隔重连；probe 端口错 → 能注册入网，但打洞永远 `PROBE_TIMEOUT`。
- **心跳配比**：客户端 `heartbeat_interval`(20s) < 服务端 `heartbeat_timeout`(60s)。配反的现象：设备周期性掉线又上线（日志反复 offline/registered）。
- **管理绑定**：`admin.bind` 默认 127.0.0.1，跨主机管理走 SSH 隧道；管理面无鉴权，不要绑公网。
- **档位**：`punch.helper_count` ∈ {256,512,1024}；启动自举 fd（需求 = 档位+1024），不足时先抬高软上限，仍不足拒绝启动并给出调限/换档建议。
- **MTU**：`tun.mtu` ≤ 1456，超了在物理链路上被分片或丢弃。
- **数据库**：空库自动按内嵌 schema 建表；预建库用 `make schema`。

## 4. 备份与恢复

- **数据库**：SQLite WAL 在线备份 `sqlite3 gtun.db ".backup '/path/backup.db'"`；恢复 = 停进程 → 覆盖 → 启动。服务器重启后链路状态自动由客户端重连上报重建，无需恢复任何内存状态。
- **身份文件**：`gtun-device-id` 与配置一起备份；**不能跨设备复制**（同一身份两处运行会互相顶替，被顶替方进程退出）。

## 5. 探活与监控

`GET /ready`（DB ping，200/503）。日志级别 warn 及以上覆盖关键路径：设备上下线、链路状态转换、打洞成败（带 reason）、TUN/路由失败。链路视图轮询 `GET /api/links`（或管理页 5s 自动刷新）。

## 6. 带宽测量与调优

### 6.1 测量方法

项目不自带测速工具，隧道建成后任何传输工具的流量都自然走隧道（互 ping 对端虚拟 IP 即路径）：

```bash
# 首选 iperf3（两端都装）
iperf3 -s                              # 对端
iperf3 -c <对端虚拟IP> -t 10           # TCP 单流；-P 4 多流；-R 反向
iperf3 -c <对端虚拟IP> -u -b 0 -t 10   # UDP 打满，看真实丢包

# 无 iperf3 时的替代（任一端起 HTTP 服务，另一端 curl 下载看 speed_download）
python3 -m http.server 8000            # 对端
curl -o /dev/null -w '%{speed_download}\n' http://<对端虚拟IP>:8000/大文件
```

定位吞吐问题时先测**不经隧道的物理基线**（同方法直连两端 LAN IP），再对照隧道数字——先分清「物理上限」还是「隧道损耗」。进阶手段：GTUN 帧头的 sequence 字段就是为抓包对账设计的（收端不去重，见 [02-公共协议层.md](02-公共协议层.md)）；客户端日志的队列满 Warn（每秒节流一条）说明数据面在丢新包。

### 6.2 实测基线与对照实验（2026-08-28，Mac arm64 ↔ Win11，同网 WiFi 局域网）

物理直连基线（不经隧道，1GB 单流 TCP）：**181 Mbit/s**。原版隧道单流约为其一半——这是**延迟问题不是算力问题**（85M ≈ 8000 包/秒，CPU 占用个位数）：用户态 TUN 让包每方向多走两次「内核↔用户态」往返，RTT 抬升后单流 TCP 吞吐（≈窗口/RTT）线性下降。对照实验（每方向完整传输 256MB，两端 `outbound/inbound_queue` 4096，原始 TCP 收发计时，同一环境连测）：

| 变体 | Mac→Win | Win→Mac | 相对原版 |
|---|---|---|---|
| 原版（mtu 1456） | 92 Mbit/s | 138 Mbit/s | — |
| A：仅放开 MTU（mtu 8000） | 146 Mbit/s | 156 Mbit/s | **+59% / +13%** |
| B：仅出站路径缩短（mtu 1456） | 86 Mbit/s | 136 Mbit/s | 波动内持平 |
| C：A+B（mtu 8000） | **165 Mbit/s** | 152 Mbit/s | **+80% / +10%** |

结论：

- **大 MTU 是明确赢家**（对应 §6.4 方案 1）：包率下降约 5.5 倍，每包固定成本（syscall/分配/调度）同步摊薄，单流达到物理基线的 **91%**（165/181）。代价是外层 IP 分片（8016B 帧拆 6 个物理分片）——局域网低丢包下实测稳定；公网有丢包放大风险，需配套自动 PMTU 探测。
- **路径缩短在本环境无可测增益**（§6.4 方案 2）：goroutine 交接每包仅省微秒级，≤2 万包/秒时瓶颈在 RTT 与 WiFi 物理层而非调度；其收益要到数十万 pps 才显现。C 的 M→W 较 A 再 +13%（146→165）但 W→M 持平，判为不显著。
- 方向差异来自测量端实现（Windows 侧 PowerShell 收包循环较慢）；各变体方法一致，相对对比有效。WiFi 环境同配置重复测量有 ±15% 波动。
- 环境注记：家用 AP 在持续大流量下出现过 2~8 分钟「ICMP 通但新建 TCP 被丢弃」的过载窗口，曾致控制面重连与保活拆链（token 守卫与重连全量上报均按设计收敛，残留 /32 由 preflight 如实拦截、`route delete` 清理）；对照实验因此改用 256MB 短载荷并带守卫重试。另：首测（1GB 口径）曾把第二个 Mac→Win 样本误标为 Win→Mac，本表数据为双向方法校正后重测，以本表为准。

### 6.3 不改代码的调优（按收益排序）

| 手段 | 做法 | 依据 |
|---|---|---|
| 多流并行 | 业务侧多条 TCP 连接，或 iperf3 `-P 4` | 单流受窗口/RTT 限制，多流填满管道——越过 100M 最实际的手段 |
| 调大队列 | `tunnel.*_queue` 4096+（内存代价 ≈ 队列×MTU，约几 MB/链路） | 吸收突发，减少丢新包触发内层 TCP 退避 |
| 核对物理 MTU | 路径不足 1500（如 PPPoE 1492）时下调 `tun.mtu`，否则外层帧被分片/丢弃 | §2.4 跨端检查 |
| 认清上行瓶颈 | 隧道无拥塞控制，家宽场景吞吐卡在双方上行，不在本软件 | 架构定位（[01-系统架构总览.md](01-系统架构总览.md)） |

### 6.4 跨平台代码层优化路线（纯 Go，三平台同一份代码）

| # | 手段 | 内容 | 收益 |
|---|---|---|---|
| 1 | **MTU 上限放开 + 自动 PMTU 探测** | 1456 上限是「外层不超物理 1500」推导的自缚；物理支持更大时放开 `tun.mtu`（协议层 `MaxTUNMTU=65491` 本就留了空间），建链时递增探测路径 MTU 替代静态配置 | 大 MTU 让 pps 按比例下降，所有每包固定成本（syscall/分配/调度）同步摊薄——结构性最大头。**已实测：仅放开至 8000 即 +59%/+13%（§6.2）** |
| 2 | **缩短 goroutine 路径** | 出站在读循环内直接「查表→编码→发送」，砍掉 `outboundSender` 交接；入站对称直达 `writeCh` | 每包少一次调度切换 ≈ 几十 μs，直接改善内层 RTT。**已实测：≤2 万包/秒时持平（§6.2），收益要数十万 pps 才显现** |
| 3 | **缓冲池 + 所有权传递** | `sync.Pool` 复用帧缓冲；`EncodeGTUNFrame` 写入调用方缓冲；macOS 前缀预置帧头；入站解码到池化缓冲 | 热路径零分配，消除高 pps 下的 GC 延迟毛刺 |
| 4 | **x/net 读写批量化** | `ipv4.PacketConn.ReadBatch/WriteBatch`：Linux 落 `recvmmsg/sendmmsg` 真加速，macOS/Windows 自动退化为单发（不吃亏） | Linux 吞吐 3~5 倍，三平台同一份代码 |
| 5 | 多路径聚合（功能立项） | helper 们建链后本就存在多条可用 UDP 路径，建成即废弃；可做 v4/v6 双栈（或多路径）striping | 近线速翻倍；需处理乱序重排，复杂度高，按功能演进立项 |

明确不做：压缩与数据面加密（拿 CPU/延迟换带宽，与受信网络定位冲突，物理越快越亏）；砍 GTUN 帧头字段（省 0.3%，毁掉抓包对账）。

**天花板账**：用户态 TUN 每包比内核转发多 4 次上下文切换，单队列的工程天花板在 2~4 Gbit/s/核（用户态 VPN 通用水平）。以上 1–4 落地后折损率可从 ~50% 压到 15% 以内；再往上（XDP/eBPF、内核模块）超出「单二进制纯 Go」定位，不纳入路线。

### 6.5 链路限速设计（方案，未实现）

**动机（真机实测，见 §6.2 环境注记）**：数据面打满链路时，廉价 AP 的连接跟踪表可能过载，丢弃新建 TCP——隧道流量把自己的控制面打死（观测到 2~8 分钟窗口：ICMP 通、新 TCP 全黑洞、隧道被保活拆链）。限速的目的是给控制面与共享链路留余量，**不是**提升吞吐。

| 维度 | 设计 |
|---|---|
| 配置 | `tunnel.rate_limit_mbps`，默认 0（不限速）；每链路独立 |
| 机制 | 令牌桶：突发额度 ≈ rate × 1s；每字节消耗一枚令牌，不足时等待 deficit/rate——平滑限速不丢包，短暂突发可容忍 |
| 位置 | 出站在 outboundSender（取包后、SendFrame 前——该 goroutine 已按链路串行，天然 pacing 点）；入站对称位置在 tunWriteLoop 消费 writeCh 处。v1 可只做出站 |
| 保活旁路 | PING 与握手控制包走 Worker 独立发送路径，不经过数据面——限速**绝不会**饿死保活，这是把限速放数据面而非 Worker 的关键理由 |
| 背压联动 | 限速后 outbound 队列更易填满，沿用既有「满则丢新包 + 内层 TCP 重传吸收」语义；建议配置校验联动（队列字节数 ≥ rate × 链路 RTT 预算） |
| 入站约束 | 入站整形不可控对端发送；但**出站限速会自然限住出站 ACK 的速率**，内层 TCP 自适应机制会把对端发送压下来——单侧限速已近似双向生效 |

不做：全局总限速（多链路场景每链路独立更有意义）；对入站丢包整形（破坏内层 TCP 语义）。

## 7. 已知边界与取舍

以下行为是精简定位下的有意取舍，不是缺陷；规模超出时按此评估：

- **对端 Online 标志会陈旧**：注册/断线只给当事设备推配置，他人的 peers.online 要等下一次管理写操作才刷新。该标志仅用于展示。
- **CONNECT 下发后双侧连接皆死时**，链路条目停在 CONNECTING，无后台回收；对该设备 QUERY 或等它重连全量上报即收敛。
- **并发管理写**（如同时加成员）可能撞虚拟 IP 的 UNIQUE 约束返回 500；单管理员串行操作不会触发。
- **出站消息无大小上限**（入站 64KB）：成员数逼近极限时配置可能超限导致客户端拒帧断连；默认单网络 8 成员远达不到。
- **设备表行数无上限**：任意 device_id 注册即落行；max_connections 只限并发会话。清理走 DELETE /api/devices/{id}。
- **网段前缀重叠不做检查**（服务端只挡完全相同网段；客户端 preflight 只拦 /32 精确冲突，不查虚拟 IP 落入其他接口已连接子网的情形）：防线是使用约定——选 10.206.x 这类冷门网段，避开物理 LAN 网段。
- **多链路并发打洞的 helper 无全局 fd 记账**：每条链路按档位创建，启动预检只覆盖「单个档位 + 冗余」；多条链路同时打洞叠加时 fd 可能不足，届时该次尝试的 helper 创建如实失败（INTERNAL_ERROR），不静默降档。单网络成员数小，实际难以触发。

## 8. 真机测试

`test/e2e/`（不使用 Docker；环境事实与踩坑记录见其 README）：

- 局域网：`real-lan.sh <本机LAN_IP> <debian_ssh>`（含双侧建成、双向 8MB MD5、保活 70s 校验）；
