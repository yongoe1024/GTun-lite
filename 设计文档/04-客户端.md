# 04 客户端（internal/client）

## 1. 模块定位

客户端是**隧道状态唯一事实来源**（见 [01-系统架构总览.md](01-系统架构总览.md) 第 6 节）：打洞成败、保活存活、链路现状只有客户端知道；控制面（TCP）断开不影响已建成的 P2P 隧道。本篇讲客户端的骨架（manager/control/数据栈/身份），打洞与保活的算法细节在 [05-NAT穿透与打洞.md](05-NAT穿透与打洞.md)。

## 2. 文件清单

| 文件 | 职责 |
|---|---|
| `config.go` | YAML 配置加载/校验（严格模式：全量必填，缺键与未知键均拒启；派生默认仅 identity.name） |
| `manager.go` | 全部本地状态 owner：数据栈（TUN+路由+数据面）与 workers 表的生命周期 |
| `worker.go` | 单条链路一次建链尝试：探测→画像→打洞→握手→保活（1089 行，算法见 05 篇） |
| `dataplane.go` | `dataStack`：preflight → 开 TUN → 装配数据面的完整序列 |
| `control.go` | 与服务器的 TCP 控制会话：注册、心跳、消息分发、重连 |
| `identity.go` | 设备身份文件的读/生成/原子写回 |
| `resources.go` | 打洞 helper socket 档位校验与创建、本机源地址选择 |
| `netutil.go` | `serverIPv4`：服务器地址解析（IP 字面量或域名 → IPv4） |
| `fdcheck_unix.go` / `fdcheck_windows.go` | fd 预算自举（RLIMIT_NOFILE） |
| `opener_darwin.go` / `opener_linux.go` / `opener_windows.go` | 平台 Opener 注入（build tag，各返回 mac/linux/win 实现） |

## 3. 启动流程（cmd/client/main.go）

`run` 按序：

1. 解析 `-config` flag（默认 `client.yaml`）→ `LoadClientConfig`（严格 YAML，KnownFields）。
2. `logging.New` 构造 logger（可选 `logging.file` / `logging.error_file` 双文件落盘，见 [08-构建配置与部署.md](08-构建配置与部署.md)）。
3. **第一个运行动作：`EnsureHelperFDHeadroom(config.Punch.HelperCount)`**——fd 预算自举（第 9 节）；不够即拒绝启动，程序绝不自行降档。
4. `LoadIdentity`：身份文件不存在则首启生成并原子写回（第 8 节）。
5. `NewManager(config, identity, PlatformOpener(), tun.NewSystemRouteTable(), log, window)`，defer manager.Close——停全部 Worker、拆数据栈与 TUN/路由（显式清理，不依赖内核回收）。
6. `NewControlClient(config, manager, identity, log, window)` → `control.Run(ctx)`（阻塞直到 ctx 取消或 duplicate_login 终态）。`window` 是 notice 窗口提示器（中文关键状态 → stderr，见 [08-构建配置与部署.md](08-构建配置与部署.md) 日志配置）。

`os.Exit(run())` 的模式与 defer 语义说明见 [08-构建配置与部署.md](08-构建配置与部署.md)。

## 4. manager：本地状态的唯一 owner

### 4.1 并发模型

触碰 manager 状态的有两类 goroutine：控制会话的读循环（收下行消息调 Handle*）与主循环（消费 Worker 事件）。约定：

- `workers` 表由 `manager.mu` 保护；
- **锁序恒为 manager.mu → plane.mu**（Register/UnregisterLink 时），无反向获取，杜绝死锁；
- Worker 在自己 goroutine 里跑，经 `events` 通道（容量 64）向 manager 汇报里程碑（WorkerConnected / WorkerFailed / WorkerProfile / WorkerLost），原子标志暴露即时状态；
- `deliverInbound`（Worker 入站回调）持 mu 只做栈指针快照即放锁——`DeliverInbound` 本身是无锁 try-send，不需要长持锁。

### 4.2 配置应用：始终全量替换

`ApplyConfig` 收到的每份 `network_config` 都是全量。不变量（也是删除配置代次 revision 的前提）：

- **拓扑未变 → 跳过重建**：`sameTUNTopology` 比较网络 ID / CIDR / 本机 IP / 对端集合（设备+配对+IP 三元组）；name 与 online 标志是展示性字段，变化不触发重建。
- **拓扑变化 → 先拆干净再重建**：preflight 执行时系统里不存在 GTun 路由，幂等成立（这也是 preflight 不需要自身路由豁免的原因，见 [03-TUN设备层.md](03-TUN设备层.md) 5.2 节）。

Worker 的去留按「幸存者」规则：

| 判定 | 条件 | 处理 |
|---|---|---|
| 幸存 | 本机 IP 未变、配对仍在、对端 IP 未变 | Worker 继续跑（**UDP 隧道不依赖 TUN**，栈重开期间 PING 保活继续），栈就绪后 `RegisterLink` 重新挂接 |
| 停止 | 其余情况 | 停 Worker |

开新栈失败时，幸存者也**如实上报失败**——不打「打洞成功却装不了数据面」的假 CONNECTED。

### 4.3 控制消息入口

| 方法 | 语义 |
|---|---|
| `HandleConnect` | 先停同配对旧 Worker（重试 = 换新 token 重建）；**栈未就绪时先重试一次开栈**——开栈失败可能是暂时性的（如悬空残留刚被清掉），重开仍失败才立即以真实原因（ROUTE_CONFLICT / TUN_CREATE_FAILED）回报失败，不闭锁到重启 |
| `HandleDisconnect` | 按 peering_id 停 Worker；token 不一致只记日志不拒绝（服务器意图权威） |
| `HandlePeerProfile` | token 不匹配的旧尝试画像直接丢弃 |
| `applyEvent` | WorkerConnected → RegisterLink；WorkerFailed/WorkerLost → stopWorker；迟到里程碑按 token 拦截 |
| `StateReport` | 全量快照**按配置枚举而非按 Worker 表**——断连期间死掉的隧道也有 IDLE 上报，纠正服务器陈旧状态 |

## 5. 数据栈（dataplane.go 的 dataStack）

`dataStack` 持有 device + RouteCleanup + plane + localIP + peerIPs，是帧转换之外的全部装配工作：

```
openDataStack:
  1. tun.CleanupDanglingHostRoutes   清掉指向已拆接口的 /32 残留（零歧义）
  2. tun.Preflight(...)              失败 → ROUTE_CONFLICT（活跃冲突仍如实报）
  3. opener.Open(...)                失败 → TUN_CREATE_FAILED（内部已回滚）
  4. tun.NewDataPlane(...).Start()
  任一步失败：回滚已建资源

close（拆栈）:
  1. cleanup.Close()   拆路由/地址——此刻接口仍在
  2. plane.Close()     关设备、停数据面
  顺序刻意如此：先拆路由再关设备（macOS 内核拆接口异步，见 03 篇 4.1 节）
```

## 6. 控制会话（control.go）

### 6.1 会话生命周期

```
Run（外层无限重连循环，固定 ReconnectInterval=5s，无指数退避）
 └─ runSession（单连接生命周期）
     1. dial 服务器（10s 超时，TCP KeepAlive 30s——读侧不设 deadline，静默由 keepalive 兜底）
     2. register：发 device_register{device_id,name,platform}
        等 device_registered / ErrorMessage / DuplicateLogin（一条连接只注册一次，
        靠 TCP 有序，无需关联 ID）
     3. awaitInitialConfig：等注册后服务器紧随推送的首份 network_config
        ——等到才 ApplyConfig + 上报全量快照（服务器可能刚重启，客户端快照
        就是它重建链路视图的唯一来源）
     4. messageLoop
     defer：尽力发 device_unregister（礼貌告别）
```

`messageLoop` 的主 select 四路：ctx 取消 / 读失败（进入下一轮重连）/ `manager.Events()`（Worker 里程碑翻译成 `profile_report` 或增量 `state_report` 发出，同时调 `manager.applyEvent` 同步本地视图）/ 心跳 ticker（发 `device_heartbeat`）。

下行分发（`handleServerMessage`）：`network_config`→ApplyConfig；`connect`→HandleConnect；`peer_profile`→HandlePeerProfile；`disconnect`→HandleDisconnect；`query`→回全量 StateReport；`duplicate_login`→返回 `ErrDuplicateIdentity`；`error`→终止本会话走重连。

### 6.2 重连为何固定 5s、无退避

断连的常见原因是服务器重启或网络抖动，可预测的固定间隔让「多久内应该恢复」有明确答案；指数退避把恢复时间变成随机变量，对运维是负资产。

### 6.3 duplicate_login 为何是进程级终态

同一身份（身份文件被复制到另一台机器）两处运行会互相顶替，形成「互相踢」的活锁。被顶替方收到 `duplicate_login` 后直接退出进程，交运维处置——身份不可跨设备复制。

## 7. 数据全链路（tun 帧 ↔ 隧道帧）

帧编解码不在 client 包：出站在 `tun/dataplane.go`（编码），入站在 `worker.go`（解码与验证）。

### 7.1 出站（本机 → 对端）

```
应用发包
 → OS 按对端 /32 主机路由送进 TUN
 → tunReadLoop 读到裸 IPv4 包（macOS 实现已剥 4 字节头）
 → ValidateIPv4Packet + src==本机虚拟IP 校验
 → 按 dst 精确查 links map → 入该链路 outbound chan（满则丢+节流）
 → outboundSender 攒批（≤32 帧）→ common.EncodeGTUNFrame 逐帧编码
 → worker.SendBatch：Linux 一次 sendmmsg 发整批，macOS/Windows 逐包 WriteToUDP
```

`WorkerLink` 实现细节：`AttemptToken` 每次发帧现取（token 会随重新打洞变化）；UDP 写不设期限——无连接语义下写阻塞不可恢复，失败即丢，可靠性由内层 TCP 重传承担。

### 7.2 入站（对端 → 本机）

```
Worker 接收 goroutine 读 UDP（前 4 字节=="GTUN" 即数据帧，否则按 P2P 控制包处理）
 → worker.deliverFrame 四级验证：
   ① 已处于 connected；
   ② 到达 socket == 选定 p2pSocket 且来源 == peerLive（helper 残留路径不算数）；
   ③ DecodeGTUNFrame（magic/长度一致/不超 MTU/IPv4 结构+头校验和——入站必验）；
   ④ 内层 src == 对端虚拟 IP 且 dst == 本机虚拟 IP（防串流与地址欺骗）
 → touchActivity() 刷新保活
 → manager.deliverInbound（持 mu 只取栈指针快照）
 → plane.DeliverInbound → 全局 writeCh（满则丢新包+节流 Warn）
 → tunWriteLoop → device.Write（macOS 实现内部补 4 字节 AF_INET 前缀）
 → 内核协议栈
```

## 8. 身份（identity.go）

- `LoadIdentity` 读身份文件；不存在则 `common.GenerateDeviceID()` 生成；
- 写回用**同目录临时文件（名带 pid）+ rename 原子安装**——截断式直写在崩溃后会留半截文件，导致以后每次启动都解析失败；
- 身份由客户端自持、服务器只登记：服务器重装后设备身份不变；
- 已知边界：并发首启的 rename 覆盖，接受（同机双开本身就被 duplicate_login 终止）。

## 9. resources 与 fd 自举

`resources.go` **不是**「要代理的网段清单」（对端清单来自服务器下发的 `NetworkConfig.Network.Peers`）：

- `helperTiers = {256, 512, 1024}`：打洞 helper socket 档位。档位决定 variable 侧 NAT 端口覆盖率，是可比较的调优旋钮；**仅此三档**，非法值 CONFIG_INVALID 拒启动，不静默取整。
- `ValidateHelperCount`：启动即拒、不降档。理由：启动时 fd 不够是配置错误，拒绝启动比静默降档更早暴露；运行期降档会让打洞成功率悄悄变化，故障排查无法复现。
- `selectLocalIPv4`：UDP connect 服务器地址，让内核选「通往服务器」的本机源地址——多宿主机（Wi-Fi+有线并存）上防止画像与打洞走不同出口。
- `CreateHelpers`：全部 helper 绑定同一本机地址，任一失败关全部（**全有或全无**，不部分成功）。

`fdcheck_unix.go` 的 `EnsureHelperFDHeadroom` 是客户端运行的第一个动作：软上限装不下「helper 档位 + 1024 冗余」时，先无特权抬高到硬上限（封顶 1<<20，防 macOS 的 RLIM_INFINITY），抬不动则 CONFIG_INVALID 拒启动。刻意不做「探测后自动选档」。Windows（`fdcheck_windows.go`）因 Winsock 句柄模型不同直接返回 nil，创建失败在打洞阶段如实暴露。

macOS 默认软上限常见为 256，连默认档位 256 都装不下——依赖自举抬高或手工 `ulimit -n 4096`。
